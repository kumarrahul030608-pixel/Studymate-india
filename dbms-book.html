Chapter 1 — Introduction to Database Systems

1.1 What is Data?

Data means raw facts that by themselves may not communicate a complete meaning. Examples include a student's roll number, name, marks, date of birth and attendance. When data is processed and interpreted, it can produce useful information. A database system exists to store and manage such data systematically.

1.2 Database and DBMS

A database is an organized collection of related data. A Database Management System is software that provides facilities to define, create, store, retrieve, update, share and protect that data. Examples of relational database systems include Oracle, MySQL and PostgreSQL.

Why not ordinary files? Independent files often create duplicate data, inconsistent values, difficult sharing, weak security and complicated recovery. A DBMS provides centralized control over these problems.

1.3 Characteristics of a Database System

Important characteristics include self-describing metadata, controlled redundancy, data sharing, multiple views, integrity constraints, security, concurrency control, backup and recovery, and transaction support.

1.4 Three-Schema Architecture

The external level contains user-specific views. The conceptual level describes the complete logical structure of the database. The internal level describes physical storage. Mappings connect these levels. This separation supports data independence.

Physical data independence: changes in storage structures should not require changes to the conceptual schema. Logical data independence: changes in the conceptual schema should have minimal effect on external views.

1.5 Database Users

Database administrators control authorization, storage, backup and overall management. Database designers define schemas and relationships. Application programmers build software using the database. End users interact through applications or query interfaces.

Chapter 2 — Data Models and ER Model

2.1 Relational Model

The relational model represents data using relations (tables). Each row is a tuple and each column is an attribute. The domain of an attribute specifies allowed values. Degree is the number of attributes and cardinality is the number of tuples.

2.2 Keys

A super key uniquely identifies tuples. A candidate key is a minimal super key. One candidate key is selected as the primary key. Remaining candidate keys are alternate keys. A foreign key references a key in another relation and supports referential integrity.

Example: Student(RollNo, Name, Email, DeptID). If RollNo and Email are each unique, both can be candidate keys; one is chosen as primary key.

2.3 Entity, Attribute and Relationship

An entity is a distinguishable real-world object. Attributes describe entities. Relationships connect entities. For example, Student enrolls in Course. Cardinality describes how many entities can participate: one-to-one, one-to-many, many-to-one or many-to-many.

2.4 Attribute Types

Simple attributes cannot be divided further; composite attributes can be divided into components. Single-valued attributes have one value per entity, while multivalued attributes may contain several values. A derived attribute can be calculated from another attribute, such as age from date of birth.

2.5 Mapping ER to Tables

Strong entities normally become tables. Simple attributes become columns. A primary key identifies each row. For a one-to-many relationship, the key of the one-side is commonly placed as a foreign key on the many-side. A many-to-many relationship is represented using an additional relation containing foreign keys from both entities.

Chapter 3 — Relational Algebra and SQL

3.1 Relational Algebra

Relational algebra is a procedural query language. Selection filters rows, projection selects columns, union combines compatible relations, difference subtracts tuples, Cartesian product pairs tuples, and join combines related tuples.

Selection: σ GPA>8(Student)
Projection: π Name,GPA(Student)
Join: Student ⋈ Student.DeptID=Department.DeptID Department

3.2 Creating Tables

CREATE TABLE Student ( roll_no INT PRIMARY KEY, name VARCHAR(50) NOT NULL, major VARCHAR(30), gpa DECIMAL(3,2) );

3.3 Insert, Update and Delete

INSERT INTO Student VALUES (10,'Rahul','CSE',8.50); UPDATE Student SET gpa=9.00 WHERE roll_no=10; DELETE FROM Student WHERE roll_no=10;

Always use an appropriate WHERE condition in UPDATE and DELETE when only selected rows should be changed.

3.4 SELECT, Filtering and Sorting

SELECT name, gpa FROM Student WHERE gpa >= 8 ORDER BY gpa DESC;

WHERE filters rows before grouping. ORDER BY controls result order. DISTINCT removes duplicate result values.

3.5 Aggregate Functions and GROUP BY

SELECT major, COUNT(*) AS total, AVG(gpa) AS average_gpa, MAX(gpa) AS highest FROM Student GROUP BY major HAVING AVG(gpa) > 7;

COUNT, SUM, AVG, MIN and MAX summarize data. HAVING filters groups after aggregation.

3.6 Joins

INNER JOIN returns matching rows. LEFT JOIN preserves every row from the left table. RIGHT JOIN preserves every row from the right table. FULL OUTER JOIN preserves rows from both sides where supported. Joins are essential when related information is stored in separate normalized tables.

3.7 Subqueries

SELECT name, gpa FROM Student WHERE gpa > (SELECT AVG(gpa) FROM Student);

The inner query calculates the average and the outer query finds students above that value.

Chapter 4 — Functional Dependencies and Normalization

4.1 Functional Dependency

X → Y means that the value of X determines the value of Y. If two tuples agree on X, they must agree on Y. Functional dependencies are used to reason about keys and good relational design.

4.2 Attribute Closure

The closure X+ is the set of attributes functionally determined by X. To calculate it, start with X, repeatedly apply dependencies whose left side is already known, and continue until no new attribute can be added. If X+ contains every attribute of the relation, X is a super key.

Example: R(A,B,C,D), F={A→B, B→C, C→D}. Start A+={A}; A→B gives B; B→C gives C; C→D gives D. Therefore A+=ABCD and A is a candidate key if it is minimal.

4.3 Anomalies

Update anomaly occurs when the same fact must be changed in multiple rows. Insertion anomaly occurs when a fact cannot be stored without another unrelated fact. Deletion anomaly occurs when deleting one fact accidentally removes another useful fact.

4.4 Normal Forms

1NF: values are atomic and repeating groups are removed. 2NF: 1NF plus no partial dependency of a non-key attribute on part of a composite candidate key. 3NF: 2NF plus no transitive dependency of non-key attributes on a key. BCNF: every determinant must be a candidate key.

Memory line: 1NF = atomic values; 2NF = remove partial dependency; 3NF = remove transitive dependency; BCNF = every determinant is a candidate key.

4.5 Lossless and Dependency-Preserving Decomposition

A decomposition is lossless if natural joining of decomposed relations does not create spurious tuples and can recover the original relation. Dependency preservation means the original functional dependencies can be enforced using the decomposed relations without needing to join them.

Chapter 5 — Transactions, Concurrency and Recovery

5.1 Transaction and ACID

A transaction is a logical unit of work such as transferring money or updating marks. Atomicity means all operations happen or none do. Consistency preserves integrity rules. Isolation controls interference between concurrent transactions. Durability makes committed changes persistent.

5.2 Transaction States

A transaction can be active, partially committed, committed, failed or aborted. A failure causes rollback or recovery actions before the transaction can be restarted or terminated.

5.3 Serializability

A serial schedule executes transactions one after another. A concurrent schedule interleaves operations. Conflict serializability can be tested using a precedence graph: create a node for each transaction and add an edge for conflicting operations ordered in the schedule. A cycle means the schedule is not conflict-serializable.

5.4 Concurrency Problems

Lost update happens when one write overwrites another. Dirty read means reading uncommitted data. Non-repeatable read means the same row changes between reads. Phantom read means a repeated condition-based query returns a changed set of rows.

5.5 Locks and 2PL

A shared lock permits reading and an exclusive lock permits writing. Two-phase locking has a growing phase for acquiring locks and a shrinking phase for releasing them. Strict 2PL keeps exclusive locks until commit or abort, helping avoid certain cascading problems.

5.6 Deadlock

Deadlock occurs when transactions wait for one another indefinitely. It can be handled through prevention, avoidance, detection and recovery. A wait-for graph containing a cycle is a classic indication of deadlock.

5.7 Recovery

Recovery brings the database back to a consistent state after failures. Log-based techniques record changes. UNDO reverses changes of transactions that should not remain, while REDO reapplies required committed changes. Checkpoints reduce the amount of log that must be processed.

START TRANSACTION; UPDATE Student SET gpa=9.10 WHERE roll_no=10; SAVEPOINT s1; UPDATE Student SET gpa=8.90 WHERE roll_no=11; ROLLBACK TO s1; COMMIT;

Chapter 6 — Query Processing, Optimization and Indexing

6.1 Query Processing

When SQL is submitted, the DBMS parses and validates it, translates it into an internal representation, considers possible execution plans, chooses an efficient plan and executes it. The objective is to reduce time and resource consumption.

6.2 Query Optimization

The optimizer can reduce intermediate results by applying selections and projections early, choose a better join order, exploit indexes and select suitable join algorithms. Optimization is important because the same logical query can have many physical execution plans with very different costs.

6.3 Indexing

An index is an additional structure that helps locate rows without scanning the complete table. B+ tree indexes support ordered and range searches. Hash indexes are particularly useful for equality searches. Indexes speed up many reads but require storage and additional work during data modification.

6.4 Practical Design Rules

Choose primary keys carefully, enforce foreign keys, normalize to an appropriate level, create indexes for frequent search/join columns, avoid unnecessary indexes, use transactions for related updates, validate inputs and always test SQL with realistic data volumes.
